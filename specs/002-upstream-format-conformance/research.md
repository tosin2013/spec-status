# Research: Upstream-format conformance

Phase 0 for [spec.md](spec.md). Each item records the decision, the reason, and what else was considered.

## R1. Exact upstream pins

- **Decision**: Pin **github/spec-kit at commit `4ca46a0706a662b1edc07086ef16f021820c2db0` (tag `v1.2.0`)** and **srobroek/speckit-roadmap at tag `v0.1.0`** (archive `refs/tags/v0.1.0.zip`, reviewed in this project on 2026-11-07).
- **Rationale**: The installed specify-cli 1.2.0 records that source in its `direct_url.json`, so the commit is known exactly, not inferred from a version number. speckit-roadmap v0.1.0 is the archive whose manifest, commands, and templates were already reviewed and installed here.
- **Alternatives considered**: Pinning by version number only (a tag can move); pinning the latest upstream `main` (unreviewed, and changes without notice).

## R2. Which template copies to pin

- **Decision**: Pin the templates as shipped in the upstream package (`specify_cli/core_pack/templates/` for Spec Kit; `templates/roadmap-template.md` for speckit-roadmap), not the copies `specify init` wrote into this project's `.specify/templates/`.
- **Rationale**: The installed copies differ from the package only by substituted command names (for example `__SPECKIT_COMMAND_TASKS__` became `/speckit-tasks`), which depend on the chosen agent integration. The package copy is the upstream source of truth and is identical for every user.
- **Alternatives considered**: Pinning the installed copies (agent-specific text would show up as drift for users of other agents).

## R3. Licenses and attribution

- **Decision**: Copy Spec Kit templates with its MIT license (`Copyright GitHub, Inc.`, from the package's `licenses/LICENSE`), and speckit-roadmap templates with its Apache-2.0 license, each with a NOTICE naming the source, pin, and copied files.
- **Rationale**: Both licenses allow copying with attribution; this matches how `testdata/speckit-roadmap-upstream` is already handled. It also kept public docs from implying a license for this project, which was unselected at the time (DC-08); the owner later chose Apache-2.0 (D-2026-11-11-02).
- **Alternatives considered**: Referencing templates by URL only (the tests would then need the network or a cache, which constitution Article II forbids at runtime and makes tests non-hermetic).

## R4. Where the drift check lives

- **Decision**: Implement the shape extractor, the conformance runner, and the drift check as Go **test files** in a new `internal/conformance` package. The drift check runs as a test that is skipped unless a candidate template path is supplied (for example `go test ./internal/conformance -run TestDrift -args -candidate=…`).
- **Rationale**: Test files are never compiled into the `spec` binary, so the runtime gains no code, dependencies, or network paths (Article II). Only the standard library is needed. The existing `imports_test.go` keeps guarding product code.
- **Alternatives considered**: A second binary under `cmd/` (would ship and be scanned as product surface); a shell script (needs extra tools and is harder to keep in step with the Go classifier); running the drift check in CI (no CI exists, and release work is unauthorized).

## R5. How "shapes" are identified

- **Decision**: Classify each line of a template or file into a **shape key** with a small, independent line classifier in the test package. Examples: `heading:2`, `item-heading`, `field:Depends on`, `field-style:bold`, `task-line`, `task-marker:[P]`, `task-marker:[USn]`, `task-id:T###`, `front-matter`, `fence`, `table`, `html-comment`, `block-quote`, `html-block`. The drift report is the set difference of shape keys between the pinned and candidate templates, plus changed field labels and task markers.
- **Rationale**: An independent classifier avoids proving the parser correct with itself. Shape keys give a reviewable vocabulary for the shape inventory (FR-003) and the drift report (FR-008). Placeholder text such as `[FEATURE NAME]` is normalized so wording changes are not reported as shape changes.
- **Alternatives considered**: A plain text diff (noisy: every wording change looks like drift); parsing with a CommonMark library (needs a dependency the constitution does not allow; also over-reports constructs that the files spec status reads never use).

## R6. Expected results and the oracle problem

- **Decision**: Each conformance fixture has a hand-written `expected.json` holding only the facts a person can count: items and their statuses, dependency states, supersession, active/verified/blocked/human-review counts, checked and total tasks, diagnostic codes with their item IDs, and the exit code at the default threshold. The runner compares these facts with the product's report and ignores everything else.
- **Rationale**: A golden file generated by the product would only test that the product agrees with itself. A hand-counted subset is the real oracle and stays stable when unrelated JSON fields grow.
- **Alternatives considered**: Byte-for-byte golden JSON (circular and brittle); comparing against a renderer (reintroduces the CommonMark bar this feature replaces).

## R7. Upstream-generated fixtures (FR-005)

- **Decision**: Use two existing sources first: (a) `testdata/speckit-roadmap-upstream`, whose four `tasks.md` files were generated by Spec Kit in the speckit-roadmap repository and whose roadmap was written by `speckit.roadmap.write`; (b) this repository's `.specify/memory/roadmap.md`, written with `speckit.roadmap.write`. Then add (c) the `tasks.md` that `/speckit-tasks` produces for this feature itself, stored unedited.
- **Rationale**: These are real upstream command outputs, not hand-built approximations. The upstream commands are agent prompts whose output varies between runs, so a stored real run is more representative than an attempt to make them deterministic.
- **Alternatives considered**: Generating outputs on every test run (needs an AI agent and the network; non-deterministic).

- **Decision**: Record the new bar as **D-2026-11-07-09** in `specs/001-spec-status/decisions.md`, marking D-2026-11-07-06 as superseded and keeping its text (history is preserved, as Article IV requires for roadmap items).

## R9. Existing visible failures

- **Decision**: Keep every fatal check added under feature 001 (closed item body, field continuation rules, fence/comment/HTML boundaries, narrow tasks dialect). The shape inventory lists upstream shapes as *supported*; the strictness rules stay as *visible failure for everything else*.
- **Rationale**: FR-014 forbids weakening visible failures, and they cost nothing on upstream-shaped files: every current conformance input already passes them.
- **Alternatives considered**: Relaxing checks that only catch exotic input (would turn visible failures back into possible silent miscounts).
